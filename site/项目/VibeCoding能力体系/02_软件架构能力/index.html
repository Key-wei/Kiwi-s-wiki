    软件架构能力：让代码库随规模优雅生长¶

    📖 本文是《AI 时代，开发者能力模型被重写》系列 · 第 2 篇 / 共 9 篇。 系列缘起与全九篇导航见 👉 系列前言（开篇）。 本篇导语：AI 是一台熵放大器——给它干净的边界，它帮你优雅填充；给它一团乱麻，它帮你把乱麻搅成灾难。这一篇讲如何用分层、DDD、Clean/Hexagonal 等架构，为 AI 生成的代码立好骨架与边界。 系列导航：← ① 产品能力 · ② 软件架构(本篇) · ③ AI 协作 →

    一、专栏简介：为什么 AI 时代架构反而更重要¶

    有一个反直觉的事实：当 AI 能在几秒内生成上百行可运行代码时，架构能力不是被削弱了，而是被空前放大了。

    过去，写代码慢，坏结构的扩散速度也慢——你还没来得及把混乱铺满整个仓库，就已经被编译错误、手写疲劳、code review 拦下来了。而现在，VibeCoding 让"生成"几乎零成本，这意味着：

    AI 是一台熵放大器。给它一个干净的边界，它帮你优雅地填充；给它一团意大利面，它帮你把面条搅成一整锅。

    具体来看，AI 辅助编码放大了三类风险：

    风险 传统开发下的表现 VibeCoding 下被放大后的表现
    结构熵增 逐渐腐化，几个月后变屎山 几天内就腐化，因为生成速度远超思考速度
    上下文丢失 人能记住"这个模块为什么这么设计" AI 每次对话都是新的，没有约束就随机发挥
    隐式耦合 手写时偶尔"顺手"耦合一下 AI 倾向于"就地取材"，把能 import 的全 import 进来

    结论很清晰：架构的本质是"约束"与"边界"。在 AI 时代，架构文档、目录结构、依赖规则不再只是给人看的规范，它们变成了喂给 AI 的护栏（guardrails）。你把边界定义得越清楚，AI 生成的代码就越收敛；你越是"让它自由发挥"，技术债累积得越快。

    这门专栏的核心主线只有一句话：高内聚、低耦合。所有架构风格——分层、DDD、Clean、Hexagonal、事件驱动——都只是达成这八个字的不同手段。请带着这条主线读完全文。

    架构关注的是"系统设计"的落地约束，而"如何权衡容量、可用性、扩展性"属于 06_系统设计能力；"如何用规范和工具让约束自动执行"属于 05_软件工程规范。本专栏聚焦代码库内部的结构。

    第 1 章 架构思想总览：约束、边界与决策¶

    核心概念：软件架构是"关于系统的、难以更改的重要决策的集合"。它的本质不是画框图，而是用约束换取长期的可维护性。

    为什么重要：每一个决策都在为未来买单或欠债。Ralph Johnson 有句名言："架构是那些让人后悔的决定。"好的架构让"改变"变得便宜——这正是熵增最快的 VibeCoding 项目最需要的能力。

    如何落地：养成对每个技术选择问三个问题：

    1. 这个决策多难反悔？（越难反悔，越需要谨慎）
    2. 它把哪些东西耦合在了一起？
    3. 半年后新人（或 AI）能否仅凭目录结构猜出业务在哪？

    在 VibeCoding 中如何用 AI：先让 AI 帮你写一份 ARCHITECTURE.md 或 ADR（Architecture Decision Record，架构决策记录），把"为什么这么分层""依赖方向是什么"写清楚，然后每次开新对话时把它作为上下文喂进去。AI 有了宪法，才不会天天违宪。

    常见误区：把"用了什么框架/技术栈"当成架构。框架是细节，架构是边界。

    实战练习：给你现在的项目写一份不超过一页的 ADR，回答"依赖方向、分层、外部系统隔离方式"三件事。

    第 2 章 分层架构（Layered Architecture）¶

    核心概念：把系统按职责水平切分，典型四层：

    表现层 (Presentation / UI / API)
        │  只能向下调用
业务层 (Application / Service)
        │
领域层 (Domain / 业务规则)
        │
数据层 (Infrastructure / DB / 外部IO)

    为什么重要：分层是"高内聚低耦合"最朴素的实现——同一职责的代码聚在一层（内聚），层与层只通过明确接口通信（低耦合）。它是所有独立开发者都应掌握的默认架构。

    如何落地：铁律——依赖只能单向向下，禁止跨层调用，禁止下层反向依赖上层。

    在 VibeCoding 中如何用 AI：在 prompt 里明确写"表现层不得包含任何业务规则，业务规则只能放在领域层"。当 AI 想在 Controller 里直接写 SQL 时，你的护栏会立刻显形。

    常见误区： - 贫血分层：分了层，但业务逻辑全漏进了表现层，领域层只剩数据结构。这是最常见的假分层。 - 传导性耦合：一个字段从 UI 一路手动传到 DB，改一个字段要动四层。

    何时不该用：极小的脚本、一次性工具，强行分层是过度设计（违反 [[08_软件设计原则]] 里的 YAGNI）。

    实战练习：把你项目里任意一个"在路由函数里直接写数据库查询"的地方，重构成 Controller → Service → Repository 三层。

    第 3 章 模块化：高内聚低耦合的量化标准¶

    这是全专栏的主线章节。

    核心概念： - 内聚（Cohesion）：一个模块内部的元素有多"该在一起"。最高级别是功能内聚（所有代码为同一个目的服务）。 - 耦合（Coupling）：模块之间的依赖强度。

    如何量化判断（给 AURA 生成代码时的检查清单）：

    信号 高内聚低耦合（好） 低内聚高耦合（坏）
    修改一个需求 只改一个模块 要改五个文件
    模块对外暴露 少量清晰接口 大量 public 字段/方法
    import 关系 依赖抽象、依赖少 到处 import 具体实现
    命名 按业务能力命名（订单、支付） 按技术类型命名（utils、helpers、common）

    警惕 utils / common / helpers：这类目录是低内聚的重灾区，它们没有明确职责，会像黑洞一样吸走一切，最终变成谁都依赖的高耦合中心。

    按业务组织，而非按技术组织（Package by Feature，而非 Package by Layer）：

    ✅ 推荐（按功能）        ❌ 不推荐（按技术类型）
/order                  /controllers
  order_service.py        order_controller.py
  order_repo.py           user_controller.py
  order_model.py        /services
/payment                  order_service.py
  payment_service.py      user_service.py
  ...                   /models  ...

    前者内聚——改订单只进 /order；后者会让每个功能的碎片散落在多个技术目录里。

    在 VibeCoding 中如何用 AI：让 AI 生成新功能前，先明确"这属于哪个业务模块，放在哪个目录"。否则 AI 默认会往 utils 里塞。

    实战练习：统计你项目里 utils.py 有多少函数，把它们按真正的业务归属拆散。

    第 4 章 领域驱动设计（DDD）¶

    核心概念：DDD（Eric Evans 提出）主张软件结构应该映射业务领域，用统一语言（Ubiquitous Language）让代码术语和业务术语一致。核心积木：

    概念 定义 例子
    限界上下文 Bounded Context 一个模型有效的边界，同一个词在不同上下文含义不同 「商品」在"目录"上下文和"库存"上下文是不同模型
    实体 Entity 有唯一标识、生命周期内可变 订单（有订单号）
    值对象 Value Object 无标识、由属性定义、不可变 金额、地址、日期区间
    聚合 Aggregate 一组必须一起保持一致的对象，有一个聚合根作为唯一入口 订单（根）+ 订单项
    领域事件 Domain Event 领域中已发生的、有业务意义的事实 「订单已支付」

    为什么重要：限界上下文是宏观层面的高内聚低耦合——它告诉你系统该在哪里切成几块。聚合则保证一致性边界，避免"改一个订单项要锁全表"。

    如何落地： 1. 先用事件风暴（Event Storming） 找出领域事件和上下文，别急着建表。 2. 值对象优先——能用不可变值对象就别用带 setter 的实体，天然减少耦合和 bug。 3. 聚合要小——聚合越大，锁竞争和耦合越严重。

    在 VibeCoding 中如何用 AI：把统一语言词汇表喂给 AI，要求它命名严格遵守业务术语（不要把「聚合根」生成成 DataManager）。让 AI 帮你做事件风暴的头脑风暴很高效。

    常见误区 / 何时不该用： - 战术模式崇拜：以为写几个 Entity/ValueObject 类就是 DDD。DDD 的精华在战略设计（上下文划分），不在战术积木。 - 过度使用：CRUD 为主、领域逻辑简单的项目（如一个博客、一个后台管理），DDD 是纯负担。DDD 适合业务复杂度高的核心域。

    实战练习：为你项目最复杂的业务对象画出它的聚合边界，问自己"哪些数据必须和它一起被修改才一致"。

    进阶阅读：Vaughn Vernon《实现领域驱动设计》比 Evans 原著更工程化、更好落地。

    第 5 章 整洁架构（Clean Architecture）与依赖倒置¶

    核心概念：Robert C. Martin（Uncle Bob）在《架构整洁之道》中提出的同心圆模型。唯一的铁律是依赖规则（The Dependency Rule）：源码依赖只能由外向内指向核心。

        ┌─────────────────────────────┐
    │   Frameworks & Drivers      │  ← Web/DB/UI（细节，最易变）
    │  ┌───────────────────────┐  │
    │  │  Interface Adapters   │  │  ← Controller/Presenter/Gateway
    │  │  ┌─────────────────┐  │  │
    │  │  │  Use Cases      │  │  │  ← 应用业务逻辑
    │  │  │  ┌───────────┐  │  │  │
    │  │  │  │ Entities  │  │  │  │  ← 企业级业务规则（最稳定）
    │  │  │  └───────────┘  │  │  │
    │  │  └─────────────────┘  │  │
    │  └───────────────────────┘  │
    └─────────────────────────────┘
      依赖箭头 ⟶ 永远向内

    关键机制——依赖倒置（DIP）：内层（业务）不能依赖外层（数据库），但业务又需要存数据怎么办？答案是内层定义接口，外层实现它：

    领域层:   interface UserRepository { save(user) }   ← 业务自己定义"我需要什么"
基础设施层: class PostgresUserRepo implements UserRepository  ← 外层来适配

    这样一来，数据库、Web 框架都变成了可插拔的细节。你的业务规则不知道自己跑在 Postgres 还是 MySQL 上——这就是终极的低耦合。

    为什么重要：它把"最易变的东西"（框架、DB、UI）推到最外层，把"最稳定的东西"（业务规则）保护在最里层。易变依赖稳定，而非反过来。

    在 VibeCoding 中如何用 AI：Clean Architecture 对 AI 极其友好——因为业务核心不依赖任何框架，AI 可以在完全不看数据库代码的情况下正确修改业务逻辑，上下文更小、更聚焦。明确要求 AI："领域层不许 import 任何 web 或 orm 库。"

    常见误区 / 何时不该用： - 小项目里，为一个只查一次的表也写 interface + 实现 + DTO 映射，会淹没在样板代码里（over-engineering）。 - 与分层架构混淆：Clean 的重点不是"层数"，而是"依赖方向"。

    实战练习：把项目里一个直接调用 ORM 的 Service，改成依赖一个自定义 Repository 接口，ORM 实现藏到基础设施层。

    第 6 章 六边形架构（Hexagonal / 端口与适配器）¶

    核心概念：Alistair Cockburn 提出。它和 Clean Architecture 思想同源，但视角是"应用 vs 外部世界"：

            [驱动侧 / 主动方]                    [被驱动侧 / 被动方]
   Web请求 ─▶ ┌──────────────────────┐ ─▶ 数据库
   CLI    ─▶ │  Port  应用核心  Port │ ─▶ 消息队列
   定时任务 ─▶ │  (业务逻辑，不知外界) │ ─▶ 第三方API
             └──────────────────────┘
             ▲ 适配器把外部协议翻译成端口调用 ▲
    • 端口（Port）：应用定义的接口（"我需要保存订单""我会被人调用来下单"）。
    • 适配器（Adapter）：端口的具体实现（REST 适配器、Postgres 适配器、Kafka 适配器）。

    为什么重要：它最大的好处是可测试性——测试时用内存适配器替换数据库适配器，业务逻辑毫秒级跑完，不需要真实 DB。同时让"换掉外部依赖"变成换一个适配器的事。

    Clean vs Hexagonal 的取舍：

    Clean Architecture Hexagonal
    视角 同心圆分层（4 层） 内外二分（核心 vs 外部）
    强调 稳定性梯度 输入/输出对称、可替换
    适合 有丰富分层业务逻辑 强调 IO 隔离、多种接入方式

    实践中两者常融合使用，不必二选一。

    在 VibeCoding 中如何用 AI：让 AI 为每个外部依赖生成"端口接口 + 一个真实适配器 + 一个测试用内存适配器"，测试覆盖率和隔离度会大幅提升。

    何时不该用：接入方式单一、几乎不换外部依赖的小工具，端口/适配器的抽象层是纯开销。

    实战练习：为项目里"发邮件"功能定义一个 NotificationPort，写一个真实适配器和一个"打印到控制台"的测试适配器。

    第 7 章 事件驱动架构（Event-Driven Architecture）¶

    核心概念：组件之间不直接调用，而是通过事件（已发生的事实） 通信。生产者发布事件，消费者订阅事件，二者互不知晓。

    [订单服务] ──发布──▶ 「订单已创建」 ──▶ [库存服务]（扣库存）
                          │──▶ [通知服务]（发短信）
                          └──▶ [积分服务]（加积分）

    为什么重要：这是时间与空间上的极致解耦。新增一个"订单创建后要做的事"，不用改订单服务一行代码——只需新增一个订阅者。这是低耦合在系统间协作层面的体现。

    核心模式： - 事件通知：只发个信号，接收方自己去查详情。 - 事件溯源（Event Sourcing）：不存当前状态，而存所有事件序列，状态由重放事件得出（martinfowler.com 有经典阐述）。 - CQRS：读写模型分离，常与事件驱动搭配。

    取舍——事件驱动的代价：

    收益 代价
    极低耦合、易扩展 难以追踪：一个业务流程散落在多个订阅者里
    天然异步、削峰 最终一致性：不再有强一致事务
    弹性、可回放 调试地狱：没有明确调用栈，需要分布式追踪

    何时不该用：单体小应用里，用事件替代普通函数调用只会让流程变得"隐形"、难以调试。同步直接调用能满足时，别引入事件。 事件驱动是为"确实需要解耦的异步/多消费者场景"准备的。

    在 VibeCoding 中如何用 AI：让 AI 维护一份"事件目录"（每个事件的名称、载荷 schema、生产者、消费者），否则事件驱动系统会迅速变成没人说得清的黑盒。

    实战练习：把项目里"下单后串行做三件事"的代码，改成发布一个领域事件、三个处理器订阅（哪怕先用进程内事件总线）。

    第 8 章 软件设计原则（SOLID / DRY / KISS / YAGNI）¶

    原则是所有架构风格背后的"物理定律"。

    SOLID：

    原则 含义 与主线的关系
    S 单一职责 一个模块只有一个变化的理由 直接服务于高内聚
    O 开闭原则 对扩展开放、对修改关闭 靠加代码而非改代码来扩展
    L 里氏替换 子类型可无缝替换父类型 保证抽象可靠
    I 接口隔离 别强迫依赖用不到的方法 降低耦合
    D 依赖倒置 依赖抽象而非具体 第 5 章的地基

    其它三条： - DRY（Don't Repeat Yourself）：消除知识的重复。注意——是消除知识重复，不是消除长得像的代码。两段巧合相似但会独立演化的代码，强行合并反而制造耦合（这叫"错误的抽象比重复更昂贵"）。 - KISS（Keep It Simple）：能简单就别复杂。 - YAGNI（You Aren't Gonna Need It）：不要为"将来可能需要"提前设计。

    在 VibeCoding 中如何用 AI 的特别提醒：AI 有两个坏倾向——过度抽象（动不动加工厂、加接口，违反 KISS/YAGNI）和复制粘贴（违反 DRY）。你要在 prompt 里明确："保持简单，不要引入当前需求用不到的抽象。" 同时在 review 时警惕重复代码。

    常见误区：把 DRY 奉为最高教条，制造出一堆参数爆炸、谁都不敢改的"万能函数"。记住优先级：KISS 和 YAGNI 通常应该压过 DRY。

    实战练习：找出你项目里最"聪明"的一个通用抽象，诚实评估它是否真的被复用了 3 次以上，否则考虑内联回去。

    第 9 章 让 AI 遵守架构约束的工程实践¶

    这是把前面所有理论落到 VibeCoding 的收口章节。

    1. 把架构写进 AI 能读到的地方 - 在仓库根放 CLAUDE.md / ARCHITECTURE.md，明确目录职责、依赖方向、命名规范。 - AI 每次生成代码前，让它先读这些约束。

    2. 用工具把约束变成"自动执行的护栏"（详见 05_软件工程规范）

    约束 自动化手段
    依赖方向不许违反 依赖检查工具（如 import-linter / ArchUnit / dependency-cruiser）
    领域层不许 import 框架 lint 规则 / CI 检查
    模块边界 目录结构 + 代码所有权

    3. 小步生成、频繁校验 不要让 AI 一次生成整个模块。按"接口先行 → 逐个用例 → 适配器"的顺序小步走，每步人工确认边界没被突破。

    4. 让 AI 做架构 review 把 diff 喂给 AI，问："这段改动有没有违反依赖规则？有没有把业务逻辑漏进表现层？" AI 既是熵的放大器，也可以是熵的检测器——取决于你怎么用它。

    核心心法：你负责定义边界，AI 负责填充边界内的实现。 边界的守护永远是人的责任。
