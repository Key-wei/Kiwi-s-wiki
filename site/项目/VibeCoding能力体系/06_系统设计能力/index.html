    系统设计能力：从数据结构到分布式的工程直觉¶

    📖 本文是《AI 时代，开发者能力模型被重写》系列 · 第 6 篇 / 共 9 篇。 系列缘起与全九篇导航见 👉 系列前言（开篇）。 本篇导语：AI 能在 30 秒写出「能跑」的功能，但「能跑」和「能扛住」之间隔着一条鸿沟。这一篇培养工程直觉：缓存、并发、锁、消息队列与经典模式，让产品从玩具变成产品。 系列导航：← ⑤ 工程规范 · ⑥ 系统设计(本篇) · ⑦ 调试能力 →

    （发布到 CSDN 等平台时，请将上方 [[...]] 替换为对应文章链接。）

    专栏简介¶

    AI 能在 30 秒内写出一个"能跑"的功能，但"能跑"和"能扛住"之间隔着一条鸿沟——这条鸿沟就叫系统设计（System Design）。

    一个用 VibeCoding 方式产出的登录接口，在你自己测试时 50ms 返回，看起来完美无缺。可当它同时被 5000 个用户请求时会发生什么？数据库连接池被打满、缓存被击穿、后台任务把主线程卡死、两个请求同时改同一行数据导致金额算错……这些问题 AI 不会主动替你想到，因为它默认你只是想"跑通"，而不是"上线扛住百万请求"。

    系统设计能力，就是让你的产品从玩具（Toy）变成产品（Product）的能力。它不是让你去背分布式论文，而是培养一种工程直觉（Engineering Intuition）：看到一段代码，能立刻问出"它的时间复杂度是多少""并发时安全吗""数据量涨 100 倍会怎样""这个热点该不该缓存"。

    对 VibeCoding 独立开发者而言，这份直觉尤其关键：因为 AI 是你唯一的"同事"，而 AI 不会 review 你的架构。你必须成为那个能提出正确问题、能识别 AI 生成代码中隐藏陷阱的人。你负责"该怎么设计"，AI 负责"把设计写出来"。 这也是本专栏与 02_软件架构能力 的分工：架构关注"模块如何切分与协作"，系统设计关注"在真实负载下如何不崩"。

    一句话：架构决定系统长什么样，系统设计决定系统能不能活下来。

    学习路线图¶

    阶段 目标 核心主题 判断标准（能独立回答/实现）
    入门 Beginner 建立复杂度与内存直觉 时间/空间复杂度、常见数据结构选型、单机缓存（LRU）、生产者消费者 "为什么这里用 HashMap 而不是 List？""这段循环是 O(n²) 吗？"
    进阶 Intermediate 掌握并发与经典模式 线程/协程/异步、锁与竞态、消息队列、事件总线、对象池、数据库索引与事务 "这段代码并发安全吗？""如何用队列削峰？""这条查询为什么不走索引？"
    精通 Advanced 面向规模与游戏级性能 ECS、数据驱动设计、Actor 模型、Job System/Task Graph、网络同步、分库分表、CAP 权衡 "10 万实体如何 60fps 更新？""缓存与 DB 如何保证一致性？""如何做水平扩展？"

    推荐节奏：入门约 2-3 周（配合刷复杂度题）；进阶约 1-2 个月（每个模式都亲手写一遍）；精通按需深入（做到哪块学哪块，游戏方向重 ECS/网络同步，Web/工具方向重数据库/分布式）。

    第一板块：基础机制¶

    第 1 章 复杂度与数据结构：一切直觉的地基¶

    核心概念：时间复杂度（Time Complexity）、空间复杂度（Space Complexity）、摊还复杂度（Amortized Complexity）。用大 O 表示法（Big-O）描述算法随输入规模增长的资源消耗趋势。

    为什么重要：这是所有系统设计判断的度量衡。你说"这样更快"，快在哪里？慢多少？没有复杂度语言，讨论性能就是玄学。AI 生成的代码经常用最直观的写法（嵌套循环、每次都 list.contains()），在小数据下毫无问题，数据一涨就指数级变慢。

    常见数据结构选型速查：

    结构 查找 插入 删除 有序 典型场景
    数组 Array O(n) O(n) O(n) 否 顺序遍历、缓存友好
    动态数组 ArrayList O(n) 摊还 O(1) 尾插 O(n) 否 通用列表
    哈希表 HashMap O(1) 均 O(1) O(1) 否 去重、索引、缓存
    平衡树 TreeMap O(log n) O(log n) O(log n) 是 范围查询、排行榜
    堆 Heap O(1) 取顶 O(log n) O(log n) 部分 优先队列、Top-K
    链表 LinkedList O(n) O(1) 已知位置 O(1) 已知位置 否 频繁头尾增删（配合 LRU）

    在 VibeCoding 中何时需要它：每次 AI 给你一段涉及"遍历+查找"的代码，问一句"内层是不是 O(n)？能不能换成 HashMap 变 O(1)？"。这是最高频、收益最大的优化直觉。

    常见误区：① 只看单次操作忽略摊还（ArrayList 尾插均摊 O(1)，个别扩容是 O(n)）；② 忽视常数与缓存局部性——理论 O(n) 的数组遍历可能比 O(log n) 的树查找更快，因为 CPU 缓存命中（见第 9 章）；③ 空间换时间用力过猛，导致内存爆炸。

    练习：把一段"双重循环找重复元素"的 O(n²) 代码改写成 O(n) 哈希表版本，并测量 10 万数据下的耗时差异。

    第 2 章 缓存：最高性价比的性能杠杆¶

    核心概念：缓存（Cache）是"用空间换时间、用一致性换速度"的经典权衡。把昂贵计算或慢速 I/O（数据库、网络）的结果暂存到快速介质（内存），下次直接命中。

    为什么重要：绝大多数 Web 系统的性能提升，第一杠杆就是缓存。一次数据库查询 5ms，一次内存命中 0.05ms，差 100 倍。命中率（Hit Rate）从 90% 提到 99%，后端压力能降一个数量级。

    缓存三大策略：

    策略 读流程 写流程 特点
    Cache-Aside（旁路，最常用） 先查缓存，未命中查库并回填 更新库，删除缓存 简单，短暂不一致
    Read/Write-Through 应用只读写缓存，缓存代管库 同步写库 一致性好，实现复杂
    Write-Back 写缓存立即返回 异步批量刷库 极快，宕机丢数据风险

    三大经典事故（面试必考、上线必踩）：

    问题 成因 解决方案
    缓存穿透 Penetration 查询不存在的 key，每次都打到库 布隆过滤器（Bloom Filter）拦截、缓存空值
    缓存击穿 Breakdown 单个热点 key 过期瞬间，大量请求同时打库 互斥锁重建、热点永不过期+后台刷新
    缓存雪崩 Avalanche 大量 key 同时过期 或缓存宕机，请求洪峰压垮库 过期时间加随机抖动、多级缓存、限流降级

    LRU 缓存原理与实现（面试高频、Redis 淘汰策略之一）：

    LRU（Least Recently Used，最近最少使用）在容量满时淘汰"最久没被访问"的项。关键是让 get 和 put 都做到 O(1)。做法：哈希表 + 双向链表。哈希表定位节点 O(1)，双向链表维护访问顺序（头部最新、尾部最旧），移动/删除节点因为双向链表可 O(1)。

    结构：
  HashMap<key, Node>          // O(1) 定位
  DoublyLinkedList            // head=最新, tail=最旧

get(key):
  if key not in map: return -1
  node = map[key]
  移动 node 到链表头部          // 标记为最新访问
  return node.value

put(key, value):
  if key in map:
      更新 value, 移动到头部
  else:
      if 已满: 删除 tail 节点(最旧) 并从 map 移除
      新建 node 插入头部, 存入 map

    时间复杂度：get/put 均为 O(1)；空间 O(capacity)。变体：LFU（按频率）、Redis 的近似 LRU（采样而非精确，节省内存）。

    在 VibeCoding 中何时需要它：任何"同样的输入反复计算/查询"的场景——用户资料、配置项、热门商品、AI 模型的 embedding 结果。先加缓存，往往比优化算法收益更大。

    常见误区：① 缓存与 DB 一致性想当然（并发下"先删缓存再更新库"与"先更新库再删缓存"都有边界问题，推荐后者+延迟双删）；② 不设过期时间导致脏数据长期存在；③ 缓存粒度过粗，改一个字段要失效一大块。

    练习：手写一个线程不安全版 LRU（HashMap+双向链表），再包一层锁做成并发安全版；对比 Redis 的 maxmemory-policy allkeys-lru 配置。

    第二板块：并发与并行¶

    第 3 章 并发模型：线程、协程与异步¶

    核心概念：并发（Concurrency，逻辑上同时处理多任务）≠ 并行（Parallelism，物理上同时执行）。实现手段有三层：线程（Thread）、协程/绿色线程（Coroutine）、异步/事件循环（Async/Event Loop）。

    三种模型对比：

    模型 调度者 切换成本 并行能力 适合 代表
    线程 Thread 操作系统内核 高（μs 级，涉及内核态） 真并行（多核） CPU 密集 Java Thread, pthread
    协程 Coroutine 用户态运行时 极低（ns 级） 单线程内并发 高并发 I/O Go goroutine, Kotlin 协程
    异步 Async 事件循环 极低 单线程并发 I/O 密集 Node.js, Python asyncio

    为什么重要：VibeCoding 做的产品几乎都是 I/O 密集型（等数据库、等 API、等磁盘）。用一个线程干等 I/O 是巨大浪费。协程/异步能让单线程在等待时切去处理别的请求，一台机器扛住成千上万连接（C10K 问题）。

    关键区分：CPU 密集（图像处理、加密、游戏物理）→ 靠多线程/多核并行；I/O 密集（Web 后端、爬虫）→ 靠异步/协程。用错了会适得其反：给 I/O 任务开一堆线程只会被上下文切换拖垮。

    在 VibeCoding 中何时需要它：AI 默认写同步阻塞代码。当你发现接口里串行 await 了 5 个独立的外部请求（本可并发），或后台有耗时任务卡住主流程时，就该引入并发。

    常见误区：① 以为"多线程一定更快"——切换和锁开销可能让它更慢；② 在异步代码里调用阻塞 API（一个同步 sleep 卡死整个事件循环）；③ 混淆并发与并行，在 Python 里指望多线程加速 CPU 计算（受 GIL 限制，得用多进程）。

    练习：把一个串行请求 3 个 API 的函数改成并发（Promise.all / asyncio.gather / goroutine + channel），测量耗时从"三者之和"降到"三者最大值"。

    第 4 章 锁与同步：互斥、读写锁、死锁与无锁¶

    核心概念：当多个执行流共享可变数据时，会产生竞态条件（Race Condition）。锁（Lock）用来保护临界区（Critical Section），保证同一时刻只有一个执行流进入。

    竞态经典例子：count++ 不是原子操作，它是"读—改—写"三步。两个线程同时执行，可能都读到 5，各自加 1 写回 6，结果丢了一次自增。

    锁的种类与取舍：

    机制 语义 开销 适用
    互斥锁 Mutex 同时仅一人进入 中 通用临界区
    读写锁 RWLock 多读并行、写独占 较高 读多写少
    自旋锁 Spinlock 忙等不睡眠 低（短临界区） 持锁极短、多核
    原子操作 Atomic 硬件级 CAS，无锁 最低 计数器、标志位

    死锁（Deadlock）四条件（同时满足才发生）：互斥、持有并等待、不可剥夺、循环等待。破解最实用的一条：统一加锁顺序（所有线程都按 A→B 顺序加锁，就不会 A 等 B、B 等 A）。

    死锁示例：
  线程1: lock(A) ... lock(B)
  线程2: lock(B) ... lock(A)   // 交叉 → 互相等待，死锁
修复：两个线程都按 lock(A) → lock(B) 顺序

    无锁（Lock-Free）：用 CAS（Compare-And-Swap，比较并交换）等原子指令避免加锁。CAS(addr, expected, new)：若当前值等于 expected 就改为 new 并返回成功，否则失败重试。优点是无阻塞、无死锁；缺点是实现极难、有 ABA 问题、高竞争下 CPU 空转。建议：独立开发者优先用成熟的并发容器（ConcurrentHashMap、sync.Map），别手写无锁结构。

    在 VibeCoding 中何时需要它：任何"多个请求/线程改同一份数据"的场景——库存扣减、余额变更、计数统计。AI 生成的 if 库存>0 { 库存-- } 在并发下会超卖，必须加锁或用数据库原子操作/乐观锁。

    常见误区：① 锁粒度太粗（锁住整个方法）导致并发退化为串行；② 忘记在异常路径释放锁（用 try-finally / RAII / defer）；③ 以为加了锁就万无一失，却在锁外读了共享变量。

    练习：写一个多线程给同一计数器加 100 万次的程序，先复现错误结果，再分别用 Mutex 和原子操作修复，对比性能。

    第 5 章 消息队列与生产者消费者：解耦与削峰¶

    核心概念：生产者-消费者模式（Producer-Consumer） 用一个队列（Queue） 作缓冲：生产者只管把任务丢进队列，消费者按自己节奏取出处理。消息队列（Message Queue, MQ） 是这个模式的分布式、持久化版本（Kafka、RabbitMQ、Redis Stream）。

    三大价值：

    价值 说明 场景
    解耦 Decoupling 生产者不需知道谁消费、怎么消费 下单后异步发短信/积分/推荐
    削峰 Peak Shaving 突发流量先入队，消费者匀速处理 秒杀、抢票
    异步 Async 耗时任务丢后台，请求立即返回 视频转码、发邮件、AI 推理

    原理示意：

    生产者 --push--> [ 队列缓冲区 ] --pull--> 消费者(可多个并行)
              (削峰/解耦)          (按处理能力消费)

同步模型:  请求 -> 处理3秒 -> 返回        (用户等3秒)
异步模型:  请求 -> 入队(10ms) -> 返回      (用户秒回)
                       └─> 后台消费者慢慢处理

    关键概念：削峰要求队列能扛住积压，消费者可水平扩展（多加几个消费者并行拉取）。需要考虑：消息确认（ACK）（处理完才确认，避免丢消息）、幂等（Idempotency）（同一消息可能被重复投递，处理逻辑要能去重）、死信队列（DLQ）（反复失败的消息隔离）。

    在 VibeCoding 中何时需要它：接口里出现"用户不必等待结果"的操作（发通知、生成报告、调用慢速 AI），或"流量可能突增"的入口。哪怕单机，用内存队列（Go channel、Python queue.Queue）+ 后台 worker 就能大幅改善体验。

    常见误区：① 用同步调用做本该异步的事，把用户晾在那等 3 秒；② 不做幂等，重复消费导致重复扣款/重复发货；③ 队列无限堆积不监控，最终 OOM。

    练习：用语言内置的阻塞队列实现一个"1 生产者 N 消费者"的图片处理管线，观察增加消费者数量对吞吐的影响。

    第三板块：经典模式¶

    第 6 章 事件总线（Event Bus）：解耦系统间通信¶

    核心概念：Event Bus（事件总线/发布订阅 Pub-Sub）是一个中心枢纽：发布者（Publisher）发出事件，订阅者（Subscriber）监听感兴趣的事件，双方互不知晓对方存在。

    为什么重要：随着功能变多，模块间直接调用会织成一张"意大利面"网络。改 A 影响 B、C、D。事件总线把这些调用变成"广播一个事件，谁关心谁处理"，实现真正的解耦。这与 02_软件架构能力 中的松耦合原则一脉相承。

    直接耦合:  下单模块 -> 直接调用 库存/积分/短信/推荐  (改一处牵四处)

事件总线:  下单模块 --publish("OrderCreated")--> [Event Bus]
                                                    ├─> 库存订阅者
                                                    ├─> 积分订阅者
                                                    ├─> 短信订阅者
                                                    └─> 推荐订阅者   (加新功能只需新增订阅者)

    在游戏中的地位：Game Programming Patterns 里的 Observer/Event Queue 模式，是解耦游戏系统（成就、音效、UI）的标准手段——玩家击杀怪物发一个 EnemyKilled 事件，成就系统、音效系统、掉落系统各自响应。

    常见误区：① 事件满天飞导致"控制流不可见"，调试时不知道谁触发了谁（配合 07_调试能力 打好事件日志）；② 同步事件总线里某个订阅者抛异常影响其他订阅者；③ 事件顺序依赖（本应无序的订阅者却暗含先后依赖）。

    练习：给一个"用户注册"功能加事件总线，让"发欢迎邮件""初始化默认设置""记录审计日志"三件事变成三个独立订阅者。

    第 7 章 对象池（Object Pool）：对抗 GC 与分配开销¶

    核心概念：Object Pool（对象池）预先创建一批对象重复使用，用完"归还"而非销毁，避免频繁的内存分配与垃圾回收（GC）。

    为什么重要：在游戏/高频场景中，每帧创建销毁成千上万的子弹、粒子、敌人，会造成两大灾难：① 内存分配开销；② GC 停顿（Stop-The-World）导致掉帧卡顿。对象池把"分配/回收"变成"从池子借/还"，成本近乎为零。

    无池:   开火 -> new Bullet()  ...  命中 -> destroy()   // 频繁 GC，掉帧
对象池: 开火 -> pool.acquire() (复用闲置对象)
        命中 -> pool.release() (标记可用, 不销毁)

池状态:  [使用中: B1 B3]  [空闲: B2 B4 B5]

    复杂度与取舍：acquire/release 均 O(1)。代价是内存常驻（池子占的内存不会释放）和状态重置（复用对象前必须清空旧状态，否则出现"上一颗子弹的伤害值残留"这类诡异 bug）。

    在 VibeCoding 中何时需要它：明确的高频短生命周期对象——游戏子弹/粒子、网络请求的 buffer、数据库连接（连接池就是对象池的特例）、线程池。反之，普通业务对象不要用池，过度池化只会增加复杂度和 bug。

    常见误区：① 忘记重置状态导致脏数据；② 池子太小频繁耗尽（退化为动态创建）或太大浪费内存；③ 归还后仍持有引用继续使用（"用了已归还对象"是最难查的 bug 之一）。

    练习：为一个粒子系统实现对象池，对比开关池化时的 GC 次数与帧率。

    第 8 章 Job System 与 Task Graph：把工作切碎喂满 CPU¶

    核心概念：Job System（作业系统） 把大任务拆成许多小 Job，丢进一个线程池，由多个 worker 线程从队列中抢活干（Work-Stealing 工作窃取），充分利用多核。Task Graph（任务图） 在此之上用有向无环图（DAG）描述 Job 之间的依赖：A、B 完成后才能跑 C。

    为什么重要：现代 CPU 有 8-16 核，单线程游戏循环只用 1 核是巨大浪费。Job System 让物理、动画、AI、剔除等系统并行跑满所有核心。Unity 的 DOTS、虚幻的 Task Graph 都基于此。

    Task Graph (依赖决定并行度):

   [输入采集]
       │
   [更新AI] ──┐
   [物理模拟]─┼──> [碰撞检测] ──> [渲染准备]
   [粒子更新]─┘
   ↑ 三者无依赖，可并行在不同核心；碰撞检测等它们都完成

worker 线程池: W1 W2 W3 W4 从全局队列 + 各自本地队列抢 Job (work-stealing 均衡负载)

    取舍：Job 太细→调度开销盖过收益；Job 太粗→负载不均，核心闲置。理想是每个 Job 几十微秒到几毫秒。依赖管理要正确，否则并行读写同一数据又回到第 4 章的竞态问题（所以常配合数据驱动设计，让 Job 只碰各自的数据）。

    在 VibeCoding 中何时需要它：做游戏或需要吃满多核的计算（批量图像处理、模拟）。Web 后端一般不需要——那里的并行由请求本身天然提供。这是"游戏/高性能方向"独立开发者的进阶技能。

    练习：用线程池实现一个简单 Job System，跑一个"1000 个独立计算任务"，对比单线程与 8 worker 的耗时。

    第 9 章 ECS 与数据驱动设计：为性能而生的架构¶

    核心概念：数据驱动设计（Data-Oriented Design, DOD） 的核心信条是"关注数据的布局与流动，而非对象"。CPU 最大的瓶颈之一是缓存未命中（Cache Miss）——从内存取数据比从 L1 缓存慢约 100 倍。DOD 让相同类型的数据在内存中连续排列，遍历时缓存命中率极高。

    ECS（Entity-Component-System，实体-组件-系统） 是 DOD 的典型落地： - Entity（实体）：只是一个 ID，本身无数据。 - Component（组件）：纯数据（Position、Velocity、Health），无逻辑。 - System（系统）：纯逻辑，批量处理拥有特定组件的所有实体。

    面向对象(OOP): 对象数组，每个对象字段散布 + 有虚函数
  [Enemy{pos,vel,hp,ai,...}][Enemy{...}]  // 遍历pos时把无关字段也拖进缓存 → cache miss

ECS/DOD: 组件按类型连续存储 (SoA, Structure of Arrays)
  Position[]: [p0][p1][p2][p3]...   ← MovementSystem 只扫这一条连续数组
  Velocity[]: [v0][v1][v2][v3]...   ← 缓存命中率极高
  MovementSystem: for i in entities: pos[i] += vel[i] * dt   // 线性遍历，SIMD 友好

    为什么重要：当实体数量达到几万几十万（弹幕、RTS 单位、粒子），OOP 的散乱内存布局会让 CPU 大量时间空等内存。ECS 把更新变成对连续数组的线性遍历，可轻松跑满 60fps，还天然适配第 8 章的 Job System 并行。

    取舍：ECS 心智负担重，代码不如 OOP 直观；小规模项目用它是过度设计。只在真正遇到大量同质实体的性能瓶颈时才上。数据驱动设计的思想（关注内存布局、批量处理、减少间接跳转）则值得在任何性能敏感场景借鉴。

    在 VibeCoding 中何时需要它：做高实体数游戏时。AI 默认会给你写 OOP 风格的 class Enemy，跑几百个没问题，上万个就卡——这时才考虑重构为 ECS。

    练习：写一个 5 万实体的移动模拟，先用 OOP（对象数组）实现，再用 SoA（Position/Velocity 分离数组）实现，测量帧时间差异，直观感受缓存的力量。

    第 10 章 Actor 模型：用消息代替共享内存¶

    核心概念：Actor 模型把并发的基本单位定义为 Actor——一个拥有私有状态、只通过异步消息与外界通信的实体。Actor 之间不共享内存，因此从根本上消除了锁和竞态（回到第 4 章的痛点）。每个 Actor 有一个邮箱（Mailbox），串行处理收到的消息。

    为什么重要："不要通过共享内存来通信，要通过通信来共享内存。" 共享内存+锁的并发模型极易出错（死锁、竞态）。Actor 用消息传递绕开这一切：既然没人共享数据，就没什么好锁的。代表：Erlang/Elixir、Akka、以及 Go 用 channel 表达的近似思想。

    共享内存并发:   多个线程 -> 争抢同一份数据 (需要锁，易死锁/竞态)

Actor 模型:     Actor A --msg--> [Actor B 邮箱] -> B 串行处理，改自己的私有状态
                Actor C --msg--> [Actor B 邮箱]
                每个 Actor 单线程处理自己邮箱 → 内部天然无竞态

    取舍：优点是高容错（Actor 崩溃可由监督者 Supervisor 重启，"Let it crash"哲学）、易水平扩展（Actor 可分布到多机）。缺点是消息传递有延迟、调试异步消息流较难、不适合需要强一致的细粒度共享状态。

    在 VibeCoding 中何时需要它：有大量独立、有状态的并发实体——聊天室每个房间一个 Actor、游戏每个玩家会话一个 Actor、IoT 每个设备一个 Actor。它与第 8 章 Job System 的区别：Actor 面向有状态的并发实体，Job System 面向无状态的可并行计算。

    练习：用 Go channel + goroutine 实现一个简单 Actor（一个 goroutine 独占一份状态，只通过 channel 收消息），做一个并发安全的计数器，全程不用锁。

    第四板块：数据与分布式¶

    第 11 章 数据库设计：范式、索引、事务、分库分表¶

    核心概念：数据库是绝大多数产品的地基。四个必须掌握的维度：

    ① 范式（Normalization）与反范式： - 范式化：消除数据冗余（用户信息只存一份，订单表存 user_id 外键）。避免更新异常。 - 反范式化：故意冗余（订单里冗余存一份用户名快照）以减少 JOIN，提升读性能。 - 取舍：写多/一致性优先→范式；读多/性能优先→适度反范式。

    ② 索引（Index）：本质是"用空间换查询时间"的排序数据结构（多为 B+ 树）。把全表扫描 O(n) 降到 O(log n)。

    概念 说明
    B+ 树索引 范围查询、排序友好，最常见
    联合索引 遵循"最左前缀"原则，(a,b,c) 能加速 a、a,b，不能单独加速 b
    覆盖索引 查询字段全在索引里，无需回表
    索引代价 加速读，但拖慢写（每次写要维护索引），占额外空间

    ③ 事务（Transaction）与 ACID：原子性（Atomicity，全成或全败）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。隔离级别从低到高：读未提交→读已提交→可重复读→串行化，隔离越强越安全但并发越差。理解脏读、不可重复读、幻读三类问题。

    ④ 分库分表（Sharding）：单表数据量过大（千万/亿级）时水平拆分。 - 分表：同库拆多表；分库：拆到多台机器。 - 分片键（Shard Key）选择是关键：按 user_id 哈希取模、或按时间范围。 - 代价：跨分片查询/JOIN/事务变得极难，全局唯一 ID 需专门方案（雪花算法 Snowflake）。能不分就不分，先用索引、缓存、读写分离顶住。

    为什么重要：AI 生成的表结构和查询往往"能用但不高效"——缺索引、N+1 查询（循环里逐条查库）、事务范围不当。数据量小时看不出，数据一涨就是全站变慢甚至宕机的头号原因。

    在 VibeCoding 中何时需要它：每次让 AI 写涉及数据库的代码，都要 review：这条查询走索引了吗？是不是 N+1？需要事务吗？事务范围是不是太大（长事务锁行导致并发下降）？

    常见误区：① 该建的索引不建、不该建的乱建；② N+1 查询（应改用 JOIN 或批量 IN 查询）；③ 用 SELECT * 拖大 I/O；④ 过早分库分表，把简单问题复杂化。

    练习：给一张百万行的表跑一条 WHERE 查询，用 EXPLAIN 看执行计划，加索引前后对比耗时；再故意写一个 N+1 查询并改成批量查询。

    第 12 章 网络同步：状态同步 vs 帧同步¶

    核心概念：多人游戏/实时协作的核心难题——如何让多个客户端在网络延迟下看到"一致"的世界。两大流派：

    维度 状态同步 State Sync 帧同步 Lockstep
    同步内容 服务器算好结果，下发状态（位置/血量） 只同步输入指令，各端本地算
    计算位置 权威服务器 每个客户端独立计算
    带宽 随实体数增长（状态大） 极小（只传输入）
    一致性要求 服务器权威即可 必须完全确定性（Determinism），各端算出完全一致的结果
    防作弊 强（服务器权威） 弱（客户端有全部数据）
    典型 FPS、MMO（守望先锋、王者部分） RTS、MOBA、格斗（星际、帧同步MOBA）

    关键技术： - 状态同步常配合：客户端预测（Client Prediction，本地先动不等服务器）、服务器和解（Reconciliation，收到权威状态后修正）、插值（Interpolation，平滑其他玩家的移动）。 - 帧同步要求：所有客户端逻辑完全确定性——不能用浮点（各平台结果可能不同，需定点数）、不能用真随机（需同种子伪随机）。一处不一致就"不同步"（游戏对不上）。

    状态同步:  客户端输入 -> 服务器计算权威状态 -> 广播状态 -> 客户端渲染/和解
帧同步:    各客户端收集全体输入(锁步) -> 本地用相同逻辑计算相同结果 -> 渲染
           (只要有一端计算不一致 → desync 灾难)

    为什么重要：这是实时多人产品的架构分水岭，选错了后期几乎无法回头。带宽、防作弊、开发难度的权衡直接决定项目可行性。

    在 VibeCoding 中何时需要它：做多人实时游戏或协作工具时。独立开发者建议：竞技/防作弊重要→状态同步（服务器权威）；RTS/大量单位/回放需求→帧同步。单机或回合制则完全不需要这套复杂度。

    练习：用两个客户端 + 一个权威服务器做一个"同步小球位置"的最小 demo，人为加 200ms 延迟，观察抖动，再加入插值和客户端预测看体验变化。
