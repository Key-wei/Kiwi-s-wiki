## 专栏简介

在 VibeCoding 时代，写代码的人变了——你不再逐行敲键盘，而是"指挥" AI 生成大段代码。这让很多独立开发者产生一个错觉：**既然 AI 写得又快又多，规范岂不是拖后腿的官僚主义？**

恰恰相反。规范在 AI 时代不是减负了，而是**权重更高了**。原因很简单：

1. **AI 生成代码的速度远超人类审查的速度。** 没有规范，你会在一周内堆出一个自己都读不懂的项目。规范是唯一能让"生成速度"不失控的刹车与护栏。
2. **AI 需要上下文（Context）才能生成好代码。** 而清晰的目录结构、README、ADR、类型定义、测试用例，本质上就是喂给 AI 的高质量上下文。**你的工程规范，就是 AI 的记忆和护栏。**
3. **未来的你 = 一个失忆的协作者。** 三个月后你回看这个项目，和一个新加入的陌生人没有区别。规范是你写给未来自己的"操作手册"。

一句话总结这个专栏的世界观：

> **规范不是束缚，而是让 AI 生成的代码可维护、让未来的你/协作者不崩溃的基础设施。文档与测试，是你给 AI 划定的护栏——护栏越清晰，AI 跑得越快越稳。**

本专栏是 [[VibeCoding能力体系]] 的第 5 篇，与 [[02_软件架构能力]]、[[04_项目管理能力]]、[[07_调试能力]] 强相关。架构决定"代码长什么样"，工程规范决定"代码如何流动、协作与守护"。

## 学习路线图

| 阶段 | 目标 | 关键动作 | 达成标志 |
|------|------|----------|----------|
| **入门**（第 1 周） | 让项目"能被读懂、能回滚" | 用 GitHub Flow + Conventional Commits；写一份像样的 README；配置 `.gitignore` 与格式化工具 | 任何一次 commit 都能说清"做了什么、为什么"；能凭 git log 回溯历史 |
| **进阶**（第 2-4 周） | 让项目"能自动守护自己" | 配置 GitHub Actions（lint + test + build）；引入 TDD 与测试金字塔；建立 PR 模板与自审清单 | 每次 push 自动跑 CI；测试覆盖核心逻辑；PR 有结构化描述 |
| **精通**（持续） | 让项目"能规模化、能协作" | 采用 Trunk-Based 或规范化分支模型；Monorepo（Turborepo/Nx）管理多包；ADR 记录架构决策；建立 AI 代码评审流程 | 多项目/多人协作不混乱；架构决策可追溯；能高效审查 AI 生成的代码 |

**核心心法**：不要一次上齐所有规范。规范应该"按痛点引入"——每当你被某个问题绊倒（找不到为什么改、CI 挂了、AI 改坏了别处），就引入对应的那一条规范。

## 第 1 章：Git 工作流

### 核心概念
Git 工作流是团队（哪怕团队只有你一个人）就"分支如何创建、合并、发布"达成的约定。三大主流模型：

| 模型 | 分支结构 | 适用场景 | 复杂度 |
|------|----------|----------|--------|
| **Git Flow** | `main` + `develop` + `feature/*` + `release/*` + `hotfix/*` | 有明确版本发布节奏的软件（如桌面 App、SDK） | 高 |
| **GitHub Flow** | `main` + 短命 `feature/*`，PR 合并即部署 | Web 应用、SaaS、独立开发者 | 低 |
| **Trunk-Based** | 几乎只有 `main`，分支存活数小时到一天 | 需要高频集成、有强 CI 的团队 | 中（依赖 CI） |

分支模型（GitHub Flow，独立开发者推荐）：

```
main   ────●────────●───────────●──────►  (始终可部署)
            \        /            \
feature      ●──●──●               ●──●   (短命，几天内合并)
```

### 为什么重要
分支模型决定了"半成品代码"如何隔离。`main` 永远保持可部署，是你最重要的安全垫——出问题时你永远有一个已知的好状态可以回退。

### 如何落地
- **独立开发者/Web 项目**：直接用 **GitHub Flow**。`main` 可部署，每个功能开一个短命分支，PR 合并。简单、够用。
- **有版本发布的库/App**：考虑 **Git Flow**（nvie 原文 *A successful Git branching model*）。
- **追求极致集成速度**：**Trunk-Based**（trunkbaseddevelopment.com），配合特性开关（feature flags）把未完成功能藏起来。

### 在 VibeCoding 中的特殊价值
AI 常常"改着改着就跑偏"，把不相关的文件也改了。**短命分支 = 小的、可丢弃的实验单元。** 如果这一轮 AI 生成的代码不满意，直接 `git checkout .` 丢掉分支，`main` 毫发无伤。把每次"让 AI 做一件事"对应一个分支，是驯服 AI 的关键习惯。

### 常见误区
- ❌ 独立开发者硬套 Git Flow，`develop`/`release` 分支形同虚设，徒增负担。
- ❌ 让功能分支活太久（几周），最后合并冲突地狱。分支越短命越好。
- ❌ 直接在 `main` 上让 AI 大改，一旦跑偏无法干净回退。

### 练习
把你当前项目切成 GitHub Flow：保护 `main`，下一个功能开 `feature/xxx` 分支，用 PR 合并。

## 第 2 章：Conventional Commits

### 核心概念
[Conventional Commits](https://www.conventionalcommits.org/) 是一套 commit message 规范，格式：

```
<type>(<scope>): <描述>

[可选正文]

[可选脚注，如 BREAKING CHANGE:]
```

常用 type：

| type | 含义 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(auth): 支持微信登录` |
| `fix` | 修 bug | `fix(api): 修复分页越界` |
| `docs` | 文档 | `docs: 补充部署说明` |
| `refactor` | 重构（不改行为） | `refactor(db): 抽取查询层` |
| `test` | 测试 | `test: 增加登录用例` |
| `chore` | 杂务/构建 | `chore: 升级依赖` |
| `perf` | 性能 | `perf: 缓存首页查询` |

### 为什么重要
提交历史是项目唯一"不会骗人"的文档。规范化的 commit 能：自动生成 CHANGELOG、配合语义化版本（SemVer）自动升版本号、让 `git log` 一眼可读。

### 如何落地
- 心里记住那张 type 表，或用 `commitlint` + `husky` 在提交时自动校验。
- 一个提交只做一件事（原子提交），描述回答"做了什么"，正文回答"为什么"。

### 在 VibeCoding 中的特殊价值
让 AI 帮你写 commit message！把 `git diff` 丢给 AI，要求它按 Conventional Commits 输出。反过来，规范的历史也让 AI 在后续对话中能快速理解"这个项目最近发生了什么"。见 [[04_项目管理能力]]。

### 常见误区
- ❌ `update`、`fix bug`、`.` 这类无信息量的 message。
- ❌ 一个 commit 塞进十个不相关改动，无法回滚单个功能。

### 练习
接下来 10 次提交全部用 Conventional Commits 格式，月底用 `git log --oneline` 回看，感受可读性差异。

## 第 3 章：Monorepo 与仓库策略

### 核心概念
**Monorepo（单体仓库）**：把多个项目/包放在同一个 Git 仓库里，用工具管理它们的依赖与构建。典型结构：

```
my-monorepo/
├── apps/
│   ├── web/          # 前端
│   └── api/          # 后端
├── packages/
│   ├── ui/           # 共享组件
│   └── config/       # 共享配置
├── turbo.json        # 或 nx.json
└── package.json
```

| 策略 | 优点 | 缺点 |
|------|------|------|
| **Monorepo** | 代码共享方便、原子提交跨包、统一工具链 | 仓库变大、需要专门工具 |
| **Polyrepo（多仓）** | 隔离清晰、权限独立 | 跨仓改动难同步、版本地狱 |

### 为什么重要
当你有"前端 + 后端 + 共享类型"时，Monorepo 让一次改动能原子地覆盖多端——尤其是共享的 TypeScript 类型定义，改一处全端受益。

### 如何落地
- **Turborepo**（官方文档 turbo.build）：轻量，专注任务编排与缓存，配置简单，适合独立开发者起步。
- **Nx**（官方文档 nx.dev）：功能全面，代码生成器、依赖图、受影响项目分析，适合更大规模。
- 核心价值都是**增量构建 + 缓存**：只重新构建"受影响"的包，CI 大幅提速。

### 在 VibeCoding 中的特殊价值
Monorepo 把相关代码放在一起，等于给 AI 提供了**完整的上下文**——AI 能看到前端调用、后端接口、共享类型，生成的代码前后一致，不会前端用了后端没有的字段。这是架构层面的护栏，参考 [[02_软件架构能力]]。

### 常见误区
- ❌ 项目还只有一个 app 就上 Monorepo，过度工程。
- ❌ 不配置缓存，CI 每次全量构建，慢到怀疑人生。

### 练习
如果你有前后端共享类型的需求，用 Turborepo 初始化一个 `apps/` + `packages/` 结构，体验共享 `packages/types`。

## 第 4 章：CI/CD

### 核心概念
- **CI（持续集成）**：每次 push 自动运行 lint、测试、构建，尽早发现问题。
- **CD（持续交付/部署）**：通过检查后自动发布到测试/生产环境。
- 理论基石：《持续交付》（*Continuous Delivery*, Jez Humble & David Farley）。

### 如何落地：GitHub Actions 实战

`.github/workflows/ci.yml` 可复制模板：

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

带部署的 CD（合并到 main 后部署）：

```yaml
  deploy:
    needs: build-and-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "在此调用 Vercel / Fly.io / 服务器部署脚本"
```

### 为什么重要
CI 是**自动化的门卫**。它保证没有人（包括 AI）能把坏掉的代码合进 `main`。CD 让"发布"从一场惊心动魄的手动仪式，变成一次无聊的自动流程。

### 在 VibeCoding 中的特殊价值
**CI 是 AI 生成代码的终极护栏。** AI 可能生成看起来对、实则跑不起来的代码。CI 会无情地告诉你：类型错了、测试挂了、构建失败了。你甚至可以把 CI 的报错日志丢回给 AI，让它自我修正——形成"AI 生成 → CI 验证 → AI 修复"的闭环。见 [[07_调试能力]]。

### 常见误区
- ❌ CI 只跑构建不跑测试，护栏形同虚设。
- ❌ CI 跑得太慢（几十分钟），大家干脆绕过它。用缓存、并行、只测受影响部分来提速。

### 练习
给现有项目加上上面的 `ci.yml`，故意提交一个类型错误，观察 CI 变红。

## 第 5 章：Code Review

### 核心概念
代码评审是合并前由人（或 AI）检查代码的过程。业界最佳实践参考 **Google Engineering Practices**（*google.github.io/eng-practices*）的 Code Review Developer Guide。核心原则一句话：

> 评审的标准不是"完美"，而是"是否明确改善了代码库的整体健康度"。

PR 自审清单模板（放进 `.github/pull_request_template.md`）：

```markdown
## 这个 PR 做了什么

## 为什么这样做

## 自审清单
- [ ] 代码符合项目规范（lint 通过）
- [ ] 增加/更新了相关测试
- [ ] 更新了相关文档
- [ ] 没有引入无关改动
- [ ] 没有硬编码的密钥/敏感信息
```

### 如何审查 AI 生成的代码（重点）
AI 生成的代码有独特的"陷阱"，审查时重点看：

| 关注点 | AI 常见问题 | 审查动作 |
|--------|-------------|----------|
| **幻觉 API** | 调用了不存在的库函数/参数 | 核对官方文档，确认 API 真实存在 |
| **过度实现** | 加了你没要求的功能/抽象 | 删掉超纲部分，保持最小改动 |
| **安全隐患** | 硬编码密钥、SQL 拼接、缺少校验 | 逐行看输入处理与鉴权 |
| **静默改动** | 顺手改了不相关的文件/逻辑 | 看完整 diff，警惕"越界"改动 |
| **似是而非** | 逻辑看起来对，边界条件错 | 亲自跑测试，别信"看起来对" |
| **风格不一致** | 与项目现有风格冲突 | 交给 linter 统一 |

**黄金法则：你对合并进 `main` 的每一行代码负全责，无论它是你写的还是 AI 写的。** 不理解就不要合并——让 AI 解释这段代码，直到你真正看懂。

### 常见误区
- ❌ "AI 写的应该没问题"直接合并——这是 VibeCoding 最大的坑。
- ❌ 评审只挑格式毛病，放过了架构与安全问题（那些应该交给自动化工具）。

### 练习
下次让 AI 生成一段代码后，逐条对照上表审查，记录你发现了几处问题。

## 第 6 章：文档驱动开发（Docs-as-Code）

### 核心概念
- **Docs-as-Code**：文档和代码一起放在仓库、一起走 PR 评审、一起版本化。
- **README**：项目门面，回答"这是什么、怎么跑起来、怎么用"。
- **ADR（Architecture Decision Record）**：架构决策记录，回答"为什么这样设计"。

README 最小模板：

```markdown
# 项目名
一句话说明这个项目是什么。

## 快速开始
​```bash
npm install
npm run dev
​```

## 技术栈 / 目录结构 / 环境变量 / 部署
```

ADR 模板（`docs/adr/0001-choose-sqlite.md`）：

```markdown
# 1. 选择 SQLite 作为初期数据库
## 状态
已接受
## 背景
独立开发者，单机部署，数据量小。
## 决策
使用 SQLite，避免运维一个独立数据库服务。
## 后果
好处：零运维、易备份。代价：并发写受限，未来可能迁移到 Postgres。
```

### 为什么重要
文档回答代码回答不了的问题——**"为什么"**。代码告诉你"是什么"，ADR 告诉你"当初为何这么选、放弃了什么"。半年后你想改架构时，ADR 能救你的命。

### 在 VibeCoding 中的特殊价值
**文档是喂给 AI 的最高质量上下文。** 一份好的 README 和 ADR，能让 AI 瞬间理解项目全貌，生成符合你架构意图的代码。反之，没有文档的项目，AI 只能靠猜。建议在仓库放一个 `AI_CONTEXT.md` 或利用 `CLAUDE.md`，专门写给 AI 看的项目约定。参考 [[02_软件架构能力]]、[[04_项目管理能力]]。

### 常见误区
- ❌ README 只有一句"我的项目"，等于没有。
- ❌ 文档和代码脱节——把文档也纳入 PR 评审即可解决。

### 练习
给当前项目写一个符合上面模板的 README，并为一个已做出的技术选型补一篇 ADR。

## 第 7 章：测试驱动开发（TDD）

### 核心概念
**TDD 循环：红 → 绿 → 重构**——先写一个失败的测试（红），写最少代码让它通过（绿），再优化代码（重构）。

**测试金字塔**（自下而上，越下越多、越快、越便宜）：

```
        /\        E2E 测试（少量，慢，贵）
       /--\       集成测试（适量）
      /----\      单元测试（大量，快，便宜）
     /______\
```

| 层级 | 测什么 | 数量 | 速度 |
|------|--------|------|------|
| 单元 | 单个函数/模块 | 最多 | 毫秒级 |
| 集成 | 模块间协作、DB/API | 中等 | 秒级 |
| E2E | 完整用户流程 | 最少 | 分钟级 |

### 为什么重要
测试是**唯一能让你放心重构的东西**。没有测试，每次改动都是在拆炸弹。有测试，你可以大胆改，因为改坏了立刻会红。

### 在 VibeCoding 中的特殊价值（AI 时代测试的新角色）
测试在 AI 时代发生了角色升级：

1. **测试 = AI 的可执行规格说明书。** 与其用自然语言描述需求，不如写好测试用例，让 AI "生成能通过这些测试的实现"。测试比自然语言精确得多。
2. **测试 = AI 代码的验收标准。** AI 说"我实现好了"，测试说了算，不是它说了算。
3. **可以让 AI 帮你补测试**，但核心业务逻辑的测试**应该由你亲自设计**——因为测试定义了"什么是对的"，这是你不能外包的判断。

推荐流程：**你写测试（定义正确性）→ AI 写实现 → CI 跑测试验证 → 循环。** 这把 TDD 和 VibeCoding 完美结合，测试成了人与 AI 之间的契约。见 [[07_调试能力]]。

### 常见误区
- ❌ 追求 100% 覆盖率，为无意义的 getter/setter 写测试。
- ❌ 全写 E2E 测试，倒金字塔，跑得慢又脆。
- ❌ 让 AI 既写实现又写测试，然后测试全绿——它可能只是写了"必然通过"的假测试。

### 练习
选一个核心函数，先写测试再让 AI 实现，体验"测试作为规格"的感觉。

## 第 8 章：把规范"喂"给 AI（VibeCoding 专章）

前面七章的规范，如何真正变成 AI 的护栏？关键是**让规范可被 AI 读取和执行**：

| 规范 | 如何变成 AI 护栏 |
|------|------------------|
| Git 工作流 | 每个 AI 任务对应一个短命分支，跑偏就丢弃 |
| Conventional Commits | 让 AI 按规范生成 commit message |
| Monorepo/结构 | 清晰目录 = AI 的导航图，减少幻觉 |
| CI/CD | AI 生成 → CI 验证 → 把报错丢回 AI 修复 |
| Code Review | 用上表逐条审查 AI 代码，绝不盲信 |
| 文档/ADR | 作为高质量上下文喂给 AI |
| 测试 | 作为可执行规格与验收标准 |

**落地建议**：在仓库根目录维护一份写给 AI 的约定文件（如 `CLAUDE.md` / `AI_CONTEXT.md`），内容包括：项目结构、技术栈、代码风格、提交规范、"不要做什么"清单。这份文件本身就是把上述所有规范"编译"成 AI 能持续遵守的护栏。

> 记住：**AI 是一个能力极强但没有长期记忆、偶尔自信满满地犯错的初级工程师。** 你的工程规范，就是你管理这个"团队成员"的制度。制度越清晰，它越靠谱。
