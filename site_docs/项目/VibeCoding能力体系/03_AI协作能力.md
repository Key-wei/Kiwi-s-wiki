## 一、专栏简介

在 VibeCoding（用 AI 辅助编码）的世界里，代码本身正在急速贬值，**"如何指挥 AI 写出正确的代码"** 正在急速升值。

很多人误以为 AI 编码的杠杆是"生成"——只要模型够强，敲一句 `帮我写个登录页` 就万事大吉。这是最大的认知误区。真正的杠杆从来不是生成，而是**指挥（Orchestration）**：

- 模型不知道你的代码库长什么样 → 你要做 **Context Engineering（上下文工程）**；
- 模型一次只能吃下有限的信息 → 你要做 **记忆窗口管理与压缩**；
- 一个 Agent 干不完一个复杂功能 → 你要做 **Multi-Agent 编排**；
- 模型需要读文件、跑测试、查数据库 → 你要做 **Tool Calling 与 MCP 接入**。

一句话总结这个专栏的核心论点：

> **Prompt 决定"这一次"AI 听不听话；Context 与 Agent 编排决定"整个系统"能不能规模化地替你干活。**

对独立开发者而言，AI 协作能力是"一个人干一个团队的活"的底层引擎。它直接决定了你的开发速度上限（关联 [[01_产品能力]] 的迭代节奏）与代码质量下限（关联 [[07_调试能力]] 的自动纠错闭环）。这不是一项软技能，而是新时代最硬核的**工程手艺**。

## 四、每章详细课程

### 第 1 章　Prompt Engineering 基础

**核心概念**：Prompt 是你与模型之间的"接口契约"。它由几个可拆解的要素组成：角色（Role）、任务（Task）、约束（Constraints）、上下文（Context）、输出格式（Output Format）。

**为什么重要**：模型是概率生成器，它输出的分布由你的 Prompt 塑造。含糊的输入必然导致含糊的输出——不是模型笨，是你没给够约束。

**方法/模式**：

| 要素 | 反面例子 | 正面写法 |
|------|----------|----------|
| 角色 | （不写） | `你是一名资深 TypeScript 后端工程师` |
| 任务 | `帮我写代码` | `实现一个带重试的 fetch 封装` |
| 约束 | （不写） | `不使用第三方库；最多重试 3 次；指数退避` |
| 输出格式 | （不写） | `只输出代码，附带 3 行以内注释` |

**VibeCoding 实战**：在 Cursor / Claude Code 里，把项目级的通用约束（技术栈、代码风格、禁用库）写进 `.cursorrules` 或 `CLAUDE.md`，就相当于给每一次对话预置了角色与约束，不必重复敲。

**常见误区**：① 把 Prompt 当"许愿池"，一句话塞十个需求；② 用礼貌用语稀释指令密度；③ 不指定输出格式，导致解析困难。

**练习**：拿你最近一次"AI 输出不满意"的对话，用上面五要素重写一遍，对比结果。

---

### 第 2 章　结构化提示与 Few-shot

**核心概念**：**结构化提示**用分隔符（XML 标签、Markdown 标题、三引号）把不同信息块隔开；**Few-shot**用少量输入-输出示例教模型"照着做"。

**为什么重要**：Anthropic 官方 Prompt Engineering 指南明确推荐用 XML 标签（如 `<context>`、`<example>`、`<instructions>`）划分区块，因为 Claude 系模型对标签边界高度敏感，能显著降低"指令与数据混淆"的错误。

**方法/模式**：

| 技巧                       | 作用        | 典型场景                        |
| ------------------------ | --------- | --------------------------- |
| XML/Markdown 分隔          | 隔离指令与数据   | 长文档摘要、代码审查                  |
| Few-shot（1-5 例）          | 锁定输出风格与结构 | 生成固定格式的 commit message、测试用例 |
| Chain-of-Thought（"逐步思考"） | 提升推理准确率   | 算法设计、Bug 根因分析               |
| Prefilling（预填响应开头）       | 强制输出格式    | 强制以 `{` 开头输出 JSON           |

**VibeCoding 实战**：让 AI 写测试时，给它 1-2 个你项目里已有的测试文件作为 few-shot 示例，生成的测试会自动贴合你的断言风格与命名规范，省去大量返工。

**常见误区**：few-shot 示例本身质量差 / 前后不一致，模型会忠实地学到你的坏习惯。示例即规范。

**练习**：为你项目写一个"生成 Conventional Commits 信息"的 3-shot 提示模板，复用到日常提交。

---

### 第 3 章　Context Engineering 上下文工程

**核心概念**：Context Engineering 是**决定放什么、不放什么进模型上下文窗口**的系统性工程。它包含四个动作：**检索（Retrieve）、筛选（Select）、压缩（Compress）、组织（Organize）**。

**为什么重要**：这是入门与精通的分水岭。模型的上下文窗口有限且昂贵，更关键的是存在 **"Context Rot / Lost in the Middle"** 现象——上下文越长、越杂，模型对中段信息的注意力越差。把整个代码库塞进去不是优势，而是灾难。**给对信息，比给多信息重要一个数量级。**

**方法/模式**：

| 手段 | 说明 | 工具体现 |
|------|------|----------|
| 语义检索（RAG） | 只捞与当前任务相关的代码片段 | Cursor 的 codebase 索引、`@file` 引用 |
| 上下文压缩 | 长历史 → 摘要，保留决策不保留过程 | Claude Code 的 `/compact`、自动 summarization |
| 分层记忆 | 常驻规则 + 会话记忆 + 检索片段 | `CLAUDE.md`（常驻）+ 对话（临时） |
| 明确引用 | 用 `@` 精准喂文件，而非让 Agent 盲搜 | Cursor `@`、Claude Code 文件路径 |
| 及时清场 | 任务切换时开新会话，避免污染 | 新开 session |

**VibeCoding 实战**：修一个 bug 时，不要把整个模块贴给 AI。先自己定位到 2-3 个相关文件，用 `@` 精确引用，再附上报错栈。上下文越干净，AI 命中率越高。长会话变慢变笨时，主动 `/compact` 或开新会话重启。

**常见误区**：① 迷信"大上下文窗口"，一股脑全塞；② 会话开太久，早期无关内容持续干扰当前任务；③ 不做压缩，token 成本失控。

**练习**：把一次"AI 越改越乱"的长会话，拆成"总结当前状态 → 开新会话 → 只带必要上下文"的两段式，感受差异。

### 第 4 章　Tool Calling 工具调用

**核心概念**：Tool Calling（函数调用）让模型从"生成文本"升级到"决定调用哪个函数、传什么参数"。模型不直接执行工具，而是输出一个结构化的调用请求，由外部运行时执行并把结果回传。

**为什么重要**：没有工具，Agent 只是个"话痨"；有了工具，它才能读文件、跑测试、查数据库、调 API——真正在你的环境里**产生副作用**。这是 Agent 从"聊天机器人"进化为"数字员工"的关键跃迁。

**方法/模式**：一次工具调用的循环是 `模型请求调用 → 运行时执行 → 结果回传 → 模型继续推理`。设计好工具是关键：

| 好工具的特征 | 说明 |
|------|------|
| 描述清晰 | 工具名与参数的 description 就是给模型的"说明书"，写烂了模型就用错 |
| 粒度合适 | 太细碎导致调用链过长，太粗则不灵活 |
| 错误可读 | 返回结构化、可诊断的错误，模型能自我纠正 |
| 幂等/安全 | 破坏性操作（删库、部署）应加确认门槛 |

**VibeCoding 实战**：Claude Code 与 Cursor Agent 内置了 read/write file、run terminal、grep 等工具，这就是它们能"自己跑测试再改代码"的原因。理解工具循环，你才知道为什么要给 AI 一条能自动跑的测试命令——它是 Agent 的反馈信号（关联 [[07_调试能力]] 的自动化验证闭环）。

**常见误区**：① 工具描述含糊，模型频繁传错参数；② 把危险操作暴露给 Agent 却不加确认；③ 工具返回一大坨无结构日志，污染上下文。

**练习**：为你的项目定义一个"运行单测并返回失败摘要"的工具/脚本，让 Agent 具备自纠错能力。

### 第 5 章　MCP 模型上下文协议

**核心概念**：**MCP（Model Context Protocol）** 是 Anthropic 于 2024 年底开源的开放协议，用于标准化"AI 应用如何连接外部工具与数据源"。它常被比喻为 **"AI 工具的 USB-C 接口"**——一次实现，处处可用。

**架构**：MCP 采用 Client-Server 模型（参见 modelcontextprotocol.io 官方规范）：

| 角色 | 职责 | 例子 |
|------|------|------|
| **Host** | 承载 AI 的应用 | Claude Desktop、Cursor、Claude Code |
| **Client** | Host 内与单个 Server 通信的连接器 | 每个 Server 一个 Client |
| **Server** | 暴露能力的独立进程 | GitHub Server、Postgres Server、文件系统 Server |

Server 向模型暴露三类原语：**Tools（可执行动作）、Resources（可读数据）、Prompts（预置提示模板）**。传输层支持 stdio（本地）与 HTTP/SSE（远程）。

**为什么重要**：在 MCP 之前，每个 AI 应用要接每个工具都得写一遍胶水代码，是 M×N 的组合爆炸。MCP 把它降为 M+N：工具方写一个 Server，AI 应用方写一个 Client，即可互通。这是 Agent 生态从"孤岛"走向"操作系统"的基础设施。

**VibeCoding 实战**：给 Claude Code / Cursor 配一个 GitHub MCP Server，AI 就能直接读 issue、开 PR；配 Postgres Server，它能直接查你的开发库 schema 再写正确的 SQL。你甚至可以自己写一个 Server，把内部工具接进任意支持 MCP 的客户端。

**常见误区**：① 装一堆 MCP Server，每个都塞工具描述进上下文，反而稀释注意力——按需启用；② 忽视权限边界，把生产库直接暴露给 Agent。

**练习**：为 Claude Code 配置一个官方文件系统或 GitHub MCP Server，观察工具列表如何进入模型上下文。

### 第 6 章　Agent Planning 任务规划

**核心概念**：Planning 是 Agent 把一个模糊大目标拆解为可执行步骤序列的能力。两大主流范式：

| 范式 | 机制 | 适用 |
|------|------|------|
| **ReAct**（Reason + Act） | 边想边做：思考→行动→观察→再思考，逐步逼近 | 探索型、环境不确定的任务（找 bug、逐步调研） |
| **Plan-and-Execute** | 先出完整计划，再逐步执行，必要时重规划 | 步骤清晰、可预估的任务（多文件重构） |

**为什么重要**：Anthropic 的《Building Effective Agents》把系统分为两类：可预测的 **Workflow（预设编排）** 与自主决策的 **Agent（模型自己规划循环）**。规划能力决定了 Agent 面对开放任务时是稳步推进还是原地打转。一个好的建议是：**能用固定 Workflow 解决的，就别用自主 Agent**——简单、可控、便宜。

**方法/模式**：显式地要求 Agent"先制定计划，经我确认后再执行"（Claude Code 的 Plan Mode 正是此思路），把规划与执行解耦，让你在昂贵的执行前有机会纠偏。

**VibeCoding 实战**：做大重构时，先让 AI 输出一份 TODO 计划清单（不写代码），你审阅调整后再让它逐条执行。这既省 token，又避免它一头扎进错误方向。

**常见误区**：① 复杂任务不做规划直接让 Agent 自由发挥，导致它在细节里迷路；② 计划粒度过粗，无法验证中间进展。

**练习**：给 AI 一个"给项目加上 i18n"的目标，要求它只输出分阶段计划，你评审后再执行第一阶段。

### 第 7 章　Agent Memory 记忆系统

**核心概念**：记忆让 Agent 跨越单次对话的边界。分三层：

| 类型 | 载体 | 生命周期 | VibeCoding 例子 |
|------|------|----------|-----------------|
| **短期记忆** | 上下文窗口 | 单次会话 | 当前对话历史 |
| **长期记忆** | 文件 / 数据库 | 跨会话持久 | `CLAUDE.md`、项目决策记录 |
| **语义记忆** | 向量数据库 | 可检索 | 代码库嵌入、历史 issue 检索 |

**为什么重要**：模型本身是无状态的——每次调用都是"失忆"重新开始。记忆系统是让 Agent"记住项目约定、上次的决策、你的偏好"的唯一办法，直接决定协作是否连贯。

**方法/模式**：

- **文件记忆**（最实用）：把"项目规则、架构决策、踩过的坑"写进 `CLAUDE.md` / `.cursorrules`，每次自动加载。这是独立开发者性价比最高的长期记忆。
- **向量记忆**：把代码/文档做 embedding 存入向量库，按语义检索相关片段注入上下文（RAG 的底座）。
- **记忆压缩**：长期记忆也要定期精简，只留"决策与结论"，去掉"过程与废话"。

**VibeCoding 实战**：每当你和 AI 达成一个重要约定（"这个项目所有日期用 UTC 存储"），立刻让它写进 `CLAUDE.md`。下次新会话，它自动记得——这就是把短期共识固化为长期记忆。

**常见误区**：① 把长期记忆当日志无限追加，越长越噪；② 依赖模型"记住"上次对话（它不会）；③ 向量检索召回一堆不相关片段污染上下文。

**练习**：整理一份你项目的 `CLAUDE.md`，包含技术栈、命名规范、3 条"血泪教训"，观察 AI 行为变化。

### 第 8 章　Multi-Agent 多智能体协作

**核心概念**：Multi-Agent 是让**多个各有专长、各有独立上下文的 Agent 协作**完成单个 Agent 难以胜任的复杂任务。核心动机是**上下文隔离**——每个子 Agent 拥有干净、聚焦的上下文窗口，避免相互污染。

**为什么重要**：Anthropic 在其多智能体研究系统（Research）的工程博客中指出，对于**可并行、需广度探索**的任务（如大规模调研），Multi-Agent 相比单 Agent 有显著提升，代价是 token 消耗大幅增加。所以它不是银弹，而是**"用成本换广度与并行度"**的权衡。

**协作拓扑**：

| 模式 | 结构 | 适用 |
|------|------|------|
| **Orchestrator-Worker（主从）** | 一个主 Agent 拆任务并派给多个 Worker，汇总结果 | 并行调研、多模块并行开发 |
| **Pipeline（流水线）** | Agent 串行接力，前者输出为后者输入 | 调研→写作→审校 |
| **Debate/Review（评审）** | 一个生成，另一个批判/审查 | 代码审查、方案对比 |
| **Hierarchical（分层）** | 多层管理，主管带小组 | 超大型任务分解 |

**VibeCoding 实战**：Claude Code 的 Subagents 功能让你为不同职责建专职 Agent——一个"研究员"负责查文档、一个"编码员"负责写实现、一个"审查员"负责挑毛病。主 Agent 编排它们，各自上下文互不干扰。

**常见误区**：① 简单任务硬上 Multi-Agent，成本翻数倍收益却为负；② 子 Agent 间职责边界不清，重复劳动或互相甩锅；③ 忽视结果汇总环节，各 Agent 输出无法整合。

**练习**：设计一个双 Agent 流程——"实现 Agent"写功能，"审查 Agent"用另一套上下文独立评审，对比单 Agent 一气呵成的质量差异。

### 第 9 章　Agent Delegation 子代理委派

**核心概念**：Delegation 是 Multi-Agent 的落地机制——主 Agent（Orchestrator）如何**把子任务委派给 Worker，并管理其生命周期与结果回收**。它是第 8 章拓扑在工程上的具体实现。

**为什么重要**：委派做得好，主 Agent 的上下文能保持极度精简（只看"任务分配"与"结果摘要"），而繁重的细节探索被隔离在各 Worker 的独立上下文里。这是让复杂 Agent 系统**可扩展、不崩窗口**的关键。

**Orchestrator-Worker 委派要点**：

| 环节 | 关键设计 |
|------|----------|
| 任务描述 | 主 Agent 给 Worker 的指令要**完整自包含**——目标、边界、期望输出格式 |
| 上下文隔离 | 每个 Worker 独立窗口，不继承主 Agent 全部历史 |
| 结果回收 | Worker 只回传**结构化摘要**，而非原始过程，保护主上下文 |
| 并行与串行 | 无依赖的子任务并行，有依赖的串行 |
| 失败处理 | 单个 Worker 失败可重试或降级，不拖垮全局 |

**VibeCoding 实战**：在 Claude Code 里，主 Agent 用 Task 工具派生一个 Subagent 去"搜索整个代码库找出所有用到旧 API 的地方"。Subagent 在自己的上下文里翻遍几十个文件，最后只回传一份"文件清单 + 行号"给主 Agent——主 Agent 的窗口丝毫不被几十个文件的内容占满。这正是"委派换取上下文清洁"的精髓（也与第 3 章 Context Engineering 一脉相承）。

**常见误区**：① 给 Worker 的指令不自包含，它缺乏背景瞎干；② 让 Worker 回传原始全文，把主上下文重新撑爆，等于没隔离；③ 过度委派，简单查询也派子 Agent，增加延迟。

**练习**：用 Claude Code 的 subagent，把一次"全库排查 + 汇总"任务委派出去，观察主会话上下文是否保持精简。

### 第 10 章　综合实战：搭一条 VibeCoding 流水线

**目标**：把前 9 章串成一条你每天都能用的自动化开发流水线。

**一条典型流水线（Orchestrator 编排）**：

1. **Context 准备**（第 3、7 章）：`CLAUDE.md` 常驻项目规则，用 `@` 精确引用相关文件。
2. **Plan**（第 6 章）：让主 Agent 先出计划，你审阅确认。
3. **Delegate 调研**（第 8、9 章）：派研究 Subagent 查文档 / 全库排查，回传摘要。
4. **Execute 编码**（第 4 章）：编码 Agent 调用 read/write/run 工具实现功能。
5. **Verify**（第 4 章 + [[07_调试能力]]）：自动跑测试，失败信息回流，Agent 自纠错。
6. **Review**（第 8 章）：独立审查 Agent 用干净上下文挑毛病。
7. **Ship**（第 5 章）：通过 GitHub MCP Server 自动开 PR。

**练习**：选一个真实小需求，全程按上述七步走一遍，记录每一步 AI 的表现与你介入纠偏的地方——这份记录本身就是最好的能力复盘。
